# FoxForge v0.1.0-alpha.2

FoxForge `v0.1.0-alpha.2` is the second public pre-release. It focuses on making the first runnable alpha more trustworthy to operate and easier to evaluate, without weakening the existing queue-safety or vendor-isolation contracts.

This is still an **early alpha**, not a production replacement for mature printer-management software.

## Highlights

- Live UI runtime feedback now distinguishes initial loading, ready state, background refresh and recoverable API failure instead of rendering failures as empty data.
- Healthy but unconfigured installations show explicit first-run empty states for printers, queue and material systems.
- Spool Inventory has its own loading/error/retry/refresh lifecycle and distinguishes a truly empty inventory from a filter with no matches.
- Printer cockpits no longer present stale, connecting, degraded, disconnected or offline telemetry as healthy live state.
- The System page reports the real API runtime state instead of claiming that UI and API are always healthy.
- Fleet and Queue read models are polled independently. A Queue-only failure no longer erases a successful Fleet snapshot, and a Fleet-only failure no longer erases already available Queue data. The combined runtime still reports an error and offers retry so partial failure is never hidden.
- English, Russian and Ukrainian remain aligned for the affected runtime, inventory, printer-state and diagnostics surfaces.
- The accepted upstream architecture strategy is now documented: Bambuddy is the primary Bambu behavior/protocol reference, PrintBuddy the multi-vendor/provider reference, PrintOps the farm/operations reference, while FoxForge owns its common domain, capability, queue, inventory, API and deployment contracts.
- FoxForge is now packaged for the user-managed `MikeFox303/umbrel-3d-printing-store` Community App Store with authenticated Umbrel App Proxy, persistent `/data` and immutable release images.

## What changed since alpha.1

### Runtime and UI reliability

- Added explicit loading, ready, refreshing and API-error presentation for live Fleet data.
- Added localized retry behavior for recoverable read failures.
- Added responsive first-run guidance for a healthy runtime with no configured printers.
- Added independent Inventory runtime state and true-empty inventory messaging.
- Added printer telemetry phases so stale/degraded/offline data cannot look healthy.
- Added honest System runtime/API status.
- Split `/api/v1/fleet` and `/api/v1/queue` into independent frontend request lifecycles while keeping the existing `FleetData` presentation boundary.

### Architecture and documentation

- Recorded ADR 0003 and the upstream adoption map for Bambuddy, PrintBuddy and PrintOps.
- Added repository guardrails so architecture-significant implementation work remains discoverable from Git rather than chat history.
- Documented the first FoxForge Umbrel Community App package, its security model and its immutable-image validation.

### Deployment

FoxForge continues to ship as one backend + compiled React web UI image for Linux `amd64` and `arm64`.

Versioned image:

```text
ghcr.io/mikefox303/foxforge:0.1.0-alpha.2
```

The release workflow builds and validates the exact release commit before publishing the multi-architecture image and GitHub pre-release. The resulting immutable digest is recorded by the release workflow and then used by the Umbrel package; no floating `latest` tag is required for installation.

The Community App package remains protected by Umbrel App Proxy authentication because FoxForge alpha does not yet provide an application-level login.

## Current API boundary

The public HTTP API remains intentionally read-only:

- `GET /healthz`
- `GET /api/v1/fleet`
- `GET /api/v1/queue`
- `GET /api/v1/inventory/spools`

`alpha.2` does **not** add anonymous printer-control, queue-mutation, inventory-mutation or remote-configuration endpoints.

This is deliberate: write APIs will be added only after authentication/authorization, request validation, idempotency, normalized error behavior and audit expectations are specified and tested.

## Safety invariants retained

- Ambiguous print starts remain `INDETERMINATE` and are never blindly retried.
- Receipt-bearing jobs are never automatically redispatched.
- Inventory owns FoxForge spool identity; printer material snapshots expose physical state and opaque slot IDs rather than `spool_id` values.
- Common application/domain code remains independent of Bambu and Moonraker transport types.
- Deep Bambu features remain typed Bambu capabilities instead of leaking vendor concepts into the common printer abstraction.
- Runtime credentials remain local and are not exposed through public read DTOs.
- Docker and Umbrel package the same FoxForge application behavior rather than separate forks.

## Known limitations

- Bambu LAN/X2D behavior is implemented and CI-tested but still needs physical-device validation for connection/reconnect, FTPS project delivery, print start, lifecycle completion and X2D-specific storage behavior.
- Moonraker/OpenKE behavior is implemented and CI-tested but still needs physical-device validation for HTTP/WebSocket connectivity, upload/start and lifecycle completion.
- ARM64 execution is exercised in CI, but representative Raspberry Pi 5/UmbrelOS hardware validation remains pending.
- Printer configuration is still file-based; there is no authenticated web flow for adding/editing credentials yet.
- Realtime WebSocket/SSE delivery is not implemented; current UI state uses polling.
- Automatic filament consumption accounting is not yet connected to print completion.
- Persistent farm scheduling, printer-selection policy and distributed runner leases are not implemented.
- Deep Bambu functions such as AMS operations/drying, HMS, K profiles, dual-nozzle control and validated X2D-specific storage remain future typed capabilities.

## Upgrade notes

`alpha.2` uses the same current runtime data locations as `alpha.1`: `/data/config.json` and the FoxForge SQLite database under `/data`.

Before upgrading an early alpha installation, keep a backup of the application data directory. Although this release does not intentionally introduce a destructive persistence migration, the project has not yet declared a stable persistence-compatibility policy.
