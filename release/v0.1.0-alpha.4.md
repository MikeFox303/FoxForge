# FoxForge v0.1.0-alpha.4

FoxForge `v0.1.0-alpha.4` is the fourth public pre-release. It packages the substantial post-`alpha.3` work now present on `main`: common Pause/Resume/Cancel controls, realtime application events, the complete operator-facing inventory workflow, and the independent-audit stabilization/security foundation.

This remains an **early alpha** intended for controlled self-hosted testing. It is not production-ready and must not be represented as physically validated on Bambu X2D, Moonraker/OpenKE, Raspberry Pi 5 or Umbrel until the repository evidence gates are satisfied with real hardware/deployment observations.

## Highlights

- Common typed Pause / Resume / Cancel capability for Bambu and Moonraker with exact observed vendor-job identity guards.
- FoxForge-owned realtime event journal plus SSE invalidation delivery with replay/resync semantics and HTTP snapshots as the source of truth.
- Full normal inventory operator workflow in the React UI: create, correct mass, edit empty-spool mass, assign/move/unassign, archive and review history.
- Atomic/idempotent inventory persistence for concurrent/restarted adjustment handling.
- Versioned persistence migrations with backups, schema validation and SQLite ownership centralized through `user_version`.
- SecretStore boundary separating Bambu access codes and Moonraker API keys from normal runtime configuration.
- Bambu LAN optional independent SHA-256 certificate pins for MQTT and FTPS, without changing compatibility defaults before real X2D validation.
- Hardened Moonraker endpoint policy covering address resolution, redirects, URL userinfo and unsafe/non-private destinations.
- Artifact quota/free-space controls, safe orphan cleanup and restart cleanup for staged print artifacts.
- Per-printer reconnect supervision with bounded global concurrency and independent backoff/jitter.
- Production-container Playwright acceptance across desktop, tablet and mobile, including printer setup, queue staging/start flow, realtime resync and inventory operations.
- Frozen dependency graphs, Dependabot, npm/pip audits, final-image vulnerability scanning and branch-aware backend coverage governance.
- Machine-checkable physical/deployment evidence manifests for the remaining AUD-003/AUD-013 and P3 resume gates.

## What changed since alpha.3

### Common job control

FoxForge now exposes a common typed job-control capability for Pause, Resume and Cancel without flattening vendor behavior into unsafe generic commands.

Safety rules remain strict:

- every command targets the exact vendor job identity currently observed by FoxForge;
- stale, unidentified or mismatched jobs are rejected before device-side execution;
- `controlId` is distinct from the HTTP `Idempotency-Key`;
- completed same-key replay does not execute the printer command again;
- ambiguous device-side outcomes are non-retryable and require explicit state reconciliation rather than blind resend.

Bambu maps the capability to native pause/resume/stop behavior. Moonraker maps it to `/printer/print/pause`, `/printer/print/resume` and `/printer/print/cancel` with native job identity revalidation.

### Realtime application events

A FoxForge-owned event journal now provides bounded replay with process epoch and monotonic sequence identity. `GET /api/v1/events` exposes Server-Sent Events for normalized application invalidations.

Realtime delivery is deliberately not a second state store:

- canonical HTTP read models remain authoritative;
- fresh, malformed, expired, foreign-process or overflowed cursors cause `resync_required`;
- frontend event handling invalidates TanStack Query families and falls back to HTTP refresh;
- queue/inventory events are published only after successful durable writes;
- raw Bambu MQTT and Moonraker WebSocket payloads are not exposed through SSE.

### Inventory workflow and persistence

The inventory UI now exposes the normal operator workflow needed before automatic filament accounting can safely resume:

- create spool;
- correct remaining mass;
- change empty-spool mass;
- assign, move and unassign slots;
- archive a spool;
- inspect adjustment/history data.

Persistence hardening now keeps adjustment idempotency, balance validation and mutation in one atomic boundary, including concurrency/restart behavior.

### Persistence, secrets and deployment security

The post-`alpha.3` source adds several stabilization layers identified by the independent project audit:

- config/schema migration ownership with backups, rollback/corruption coverage and SQLite `user_version`;
- application SecretStore for Bambu access codes and Moonraker API keys, including migration of legacy inline credentials;
- explicit standalone/deployment bearer-token trust model with production fail-closed behavior;
- representative reverse-proxy tests proving forwarded/authenticated-user headers do not become an application principal;
- explicit deployment-auth contract tests for read-only/no-token, valid-token write and invalid-token rejection behavior.

Backups of `/data` must therefore be treated as credential-bearing data.

### Bambu and Moonraker transport hardening

Bambu LAN supports optional independent certificate fingerprints for MQTT and FTPS. A mismatch fails closed without disclosing the expected fingerprint. The default compatibility behavior is unchanged until representative X2D observations are recorded.

Moonraker composition now validates resolved destinations against explicit private-network policy, rejects unsafe mixed DNS results, redirects and URL userinfo, and requires deliberate overrides for public/loopback/link-local destinations.

### Artifact lifecycle and reconnect behavior

Artifact staging now enforces configured capacity and minimum free-space reserves, performs safe stale-temp/orphan cleanup and never garbage-collects artifacts referenced by the durable queue.

Reconnect supervision now uses per-printer workers with bounded global concurrency, independent exponential backoff/jitter and dynamic worker discovery so one unreachable printer does not serialize the entire fleet.

### Browser and CI governance

The repository now includes frozen npm/pip dependency inputs, Dependabot, dependency audits, final-image HIGH/CRITICAL vulnerability scanning, production-container Playwright acceptance and measured Python branch coverage.

The backend baseline is approximately 76% branch-aware coverage with a 75% CI non-regression floor. Python 3.12 and 3.13 both run the backend suite; Python 3.12 is the release runtime.

## Independent audit status in this release

All software-only findings from the 2026-09-04 independent audit have repository remediation evidence. The remaining unresolved items are validation-bound rather than missing software foundations:

- **AUD-003 — VALIDATION REQUIRED:** representative future Umbrel/package validation must prove install/restart persistence, authenticated proxy writes, direct-backend fail-closed behavior, deployment-network printer reachability and realtime reconnect/resync.
- **AUD-013 — VALIDATION REQUIRED:** representative Bambu X2D MQTT/FTPS certificate observations must prove correct-pin success, independent wrong-pin fail-closed behavior and restart/recovery stability.

The repository now contains a strict physical-evidence verifier for those findings and for the eventual P3 resume gate.

## P3 automatic filament accounting

Automatic filament accounting is **not included** in `alpha.4`.

The partial P3 implementation remains intentionally frozen in draft PR #58. The normal inventory operator prerequisite is complete, but P3 must not resume or merge until representative X2D, Moonraker/OpenKE and Raspberry Pi/Umbrel evidence satisfies the recorded physical/deployment gate and the draft is synchronized with the then-current `main`.

- release manifest/backend/frontend identity consistency;
- frozen backend dependency installation;
- Ruff lint and formatting checks;
- full backend pytest suite;
- frozen frontend dependency installation;
- TypeScript typecheck;
- Vitest unit tests;
- Vite production build;
- unified release-image build and live `/healthz`/SPA/persistence smoke;
- Linux `amd64` + `arm64` multi-architecture image publication with SBOM/provenance;
- immutable Git tag creation;
- GitHub pre-release creation only after the preceding gates succeed.

The semantic Git tag, GitHub release and GHCR version tag are preflight-checked for uniqueness and are never overwritten by the normal development-image workflow.

## Known limitations

- Physical Bambu X2D validation remains required for connection/reconnect, state sync, MQTT/FTPS certificate behavior, project delivery, print-start acknowledgement, Pause/Resume/Cancel, lifecycle completion and ambiguous-outcome handling.
- Physical Moonraker/OpenKE validation remains required for endpoint-policy compatibility, HTTP/WebSocket behavior, upload/checksum/start, Pause/Resume/Cancel and lifecycle completion/failure handling.
- Representative Raspberry Pi 5/UmbrelOS installation, restart/persistence, real proxy auth boundary, printer-network reachability, upgrade and SSE reconnect/resync validation remains incomplete.
- Bambu certificate pinning is available but compatibility defaults are intentionally unchanged pending physical X2D evidence.
- Realtime uses SSE invalidation plus HTTP truth; polling remains as an alpha fallback.
- Automatic filament accounting remains frozen and is not shipped from PR #58.
- Persistent farm scheduling/distributed leases are not implemented.
- Deep Bambu AMS/CFS operations, drying, HMS actions, K profiles, dual-nozzle controls and other vendor-depth work remain future typed capabilities.
- Persistence compatibility is still pre-stable. Back up the complete `/data` directory before upgrading.

## Upgrade notes

`alpha.4` continues to use persistent `/data` for configuration, SQLite state, secrets and staged artifacts. This release adds migration/secret-storage machinery, so a complete backup of `/data` is strongly recommended before upgrading from `alpha.3`.

Do not copy individual config/database files as if they were non-sensitive: current `/data` backups may contain printer credentials or credential-recovery material.

The companion Umbrel Community App must be updated separately after this release workflow publishes the immutable `alpha.4` image digest. The Store package should pin that digest rather than a floating tag.
