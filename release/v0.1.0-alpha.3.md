# FoxForge v0.1.0-alpha.3

FoxForge `v0.1.0-alpha.3` is the third public pre-release. It turns the previously read-mostly alpha into a guarded, authenticated management workflow for printer configuration, filament inventory and print submission while preserving FoxForge's strict queue-safety and vendor-isolation contracts.

This remains an **early alpha**. It is intended for evaluation and controlled self-hosted testing, not unattended production use.

## Highlights

- Authenticated FoxForge command layer with explicit permissions, request correlation, durable HTTP idempotency, normalized errors and append-only command audit.
- Browser operator-session support for trusted self-hosted UI command workflows.
- Printer setup API and UI for add/update/remove/test/reconnect without exposing stored credentials through public read models.
- Authenticated filament inventory mutations for spool creation, corrections, empty-spool mass changes, assignment/move/unassign and archive.
- Restart-safe content-addressed `.gcode` / `.3mf` staging under `/data/artifacts` with SHA-256 verification and bounded uploads.
- Authenticated/idempotent queue enqueue, explicit dispatch and explicit reconciliation endpoints.
- Safe browser print workflow: select a local file, hash it in the browser, upload bytes only, enqueue it, then explicitly start the print.
- Correct separation of durable queue `dispatch_id` from per-command HTTP `Idempotency-Key`.
- `INDETERMINATE` remains reconciliation-only: the UI never offers blind retry for an ambiguous printer side effect.
- Retry controls are exposed only for backend-confirmed retryable, receipt-free pre-start failures.
- EN/RU/UK localization remains key-parity tested across the new command workflow.
- Unified Docker runtime and multi-architecture Linux `amd64` + `arm64` publication remain the release target.

## What changed since alpha.2

### Command security and audit

`alpha.2` intentionally exposed only read APIs. `alpha.3` introduces the first guarded write boundary defined by ADR 0004:

- fail-closed authentication;
- explicit principal permissions;
- request IDs for command correlation;
- durable idempotency records so uncertain HTTP retries can replay the same logical request safely;
- conflict detection when the same idempotency key is reused with a materially different payload;
- normalized command error responses;
- append-only SQLite command audit;
- raw bearer tokens and raw idempotency keys are not persisted in audit records.

These controls are application-level. Umbrel App Proxy remains defense in depth rather than the sole command authorization boundary.

### Printer configuration

FoxForge now supports authenticated application-managed printer configuration flows:

- add a printer;
- update configuration;
- remove a printer;
- test configuration/connectivity;
- reconnect a configured printer.

The web application now exposes the printer setup launcher rather than leaving Add Printer disabled.

### Queue and artifact staging

The public print path now has an explicit staged boundary:

```text
browser File
   |
SHA-256 in browser
   |
POST /api/v1/artifacts
(bytes only; no client filesystem path)
   |
verified content-addressed artifact
   |
POST /api/v1/queue
   |
durable queue entry + dispatch_id
   |
POST /api/v1/queue/{id}/dispatch
   |
accepted | blocked | failed | INDETERMINATE
                              |
                    explicit reconciliation only
```

Important safety rules:

- no public route accepts an arbitrary server-side filesystem path;
- the selected client path is never transmitted by the browser;
- artifact identity is the verified SHA-256 digest;
- queue `dispatch_id` is a durable logical printer-dispatch identity;
- HTTP `Idempotency-Key` identifies one remote command attempt and is preserved across uncertain network replay;
- a completed `BLOCKED` or explicitly retryable receipt-free pre-start failure may later be reassessed with a new HTTP key while keeping the same queue `dispatch_id`;
- receipt-bearing jobs are never redispatched;
- `INDETERMINATE` cannot be bypassed with another start request.

### Inventory writes

The durable SQLite inventory can now be mutated through authenticated/idempotent command endpoints for:

- spool creation;
- mass corrections;
- empty-spool mass updates;
- slot assignment, movement and unassignment;
- archival.

The existing exact `Decimal` accounting, immutable adjustment history and assignment uniqueness rules remain intact.

### Web UI

The React client now includes:

- authenticated printer setup;
- local `.gcode` / `.3mf` selection;
- browser SHA-256 calculation;
- byte-only staged upload;
- durable queue enqueue;
- a separate explicit Start print action;
- safe replay wording that distinguishes resending the same HTTP request from starting another physical print;
- explicit started/not-started reconciliation for `INDETERMINATE` entries;
- responsive/mobile refinements and real repository-build screenshots.

## API boundary in alpha.3

Read models remain available for health, fleet, queue and inventory. Guarded write routes now additionally cover printer configuration, inventory mutations, artifact staging and queue enqueue/dispatch/reconciliation.

Remote mutations remain subject to ADR 0004. This release does **not** add a generic unrestricted printer-command endpoint.

## Not included in alpha.3

The following work is intentionally outside the frozen release candidate:

- common Pause / Resume / Cancel controls;
- the unfinished `feature/job-control-capability` branch;
- realtime WebSocket/SSE application-event delivery;
- automatic queue-to-filament consumption accounting;
- persistent farm scheduling and distributed leases;
- deep Bambu AMS operations/drying, HMS actions, K profiles, dual-nozzle controls and unvalidated X2D-specific storage behavior.

## Known limitations

- Physical Bambu LAN/X2D validation is still required for connection/reconnect, project delivery, print-start acknowledgement, lifecycle completion and ambiguous-start reconciliation on representative hardware.
- Physical Moonraker/OpenKE validation is still required for HTTP/WebSocket connectivity, upload/start and lifecycle completion/failure behavior.
- Representative Raspberry Pi 5/UmbrelOS printer-network, restart, persistence and upgrade validation remains incomplete even though Linux ARM64 images are built in CI.
- Browser file hashing currently uses WebCrypto over the selected file contents; very large files may require a future incremental/streaming hashing implementation for lower browser memory use.
- Realtime application events are not implemented; the UI continues to use polling.
- Inventory command APIs exist, but the full inventory mutation UI is not yet complete.
- The project has not yet declared stable persistence compatibility; back up `/data` before upgrading between early alpha builds.

## Upgrade notes

`alpha.3` continues to use persistent `/data/config.json`, `/data/foxforge.sqlite3` and now `/data/artifacts` for staged print payloads.

Before upgrading from `alpha.2`, back up the FoxForge application data directory. The release is designed to preserve existing alpha data, but persistence compatibility is still pre-stable.

The companion Umbrel Community App must be updated separately after the release workflow publishes the immutable `alpha.3` image digest. Do not replace the package with a floating image tag.

## Container image

After the guarded release workflow succeeds, the versioned image is:

```text
ghcr.io/mikefox303/foxforge:0.1.0-alpha.3
```

The workflow publishes Linux `amd64` and `arm64` with SBOM/provenance metadata and records the resulting multi-architecture digest.
