# FoxForge v0.1.0-alpha.1

FoxForge `v0.1.0-alpha.1` is the first public pre-release of the project and the first unified runnable FoxForge application.

This release is intended for early testing, development and architecture validation. It is **not production-ready** and should not yet be treated as a replacement for mature printer-management software.

## Highlights

- Unified FoxForge backend + React web UI served from one application runtime.
- Vendor-independent `PrinterAdapter` architecture with typed capability discovery.
- Bambu Lab adapter foundation with LAN MQTT/TLS, implicit FTPS project delivery and fail-safe ambiguous-start handling.
- Moonraker/Klipper adapter foundation with HTTP/WebSocket state, upload and print-start transport.
- Durable SQLite-backed print queue with explicit `INDETERMINATE` safety semantics and bounded retry policy.
- Durable filament/spool inventory with exact Decimal mass accounting, immutable idempotent adjustments and physical-slot assignments.
- Read-only public HTTP API v1 for health, fleet, queue and inventory snapshots.
- React + TypeScript + Vite interface using live `/api/v1` data in normal runtime mode.
- English, Russian and Ukrainian interface localization.
- Standalone Docker deployment with persistent `/data`, non-root steady-state execution and startup smoke tests.
- Multi-architecture GHCR image publication for Linux `amd64` and `arm64`.

## Container image

The versioned image for this pre-release is:

```text
ghcr.io/mikefox303/foxforge:0.1.0-alpha.1
```

Example:

```bash
docker run -d \
  --name foxforge \
  --restart unless-stopped \
  -p 8420:8000 \
  -v foxforge_data:/data \
  ghcr.io/mikefox303/foxforge:0.1.0-alpha.1
```

Then open `http://<server-ip>:8420`.

On first start FoxForge creates a safe empty `/data/config.json` and the application SQLite database. Printer connection failures do not prevent the web/API process from starting.

## Current API boundary

The public API is intentionally read-only in this release:

- `GET /healthz`
- `GET /api/v1/fleet`
- `GET /api/v1/queue`
- `GET /api/v1/inventory/spools`

Printer-control, queue-mutation, inventory-mutation and remote configuration endpoints are not exposed yet. Matching UI write controls remain unavailable until authenticated command contracts exist.

## Known limitations

- Bambu LAN/X2D transport is implemented and CI-tested but still requires physical-device validation for connectivity, storage delivery, print start and lifecycle completion.
- Moonraker/OpenKE transport is implemented and CI-tested but still requires physical-device validation for connectivity, upload/start and lifecycle completion.
- ARM64 images are built through the multi-architecture release pipeline, but representative-device runtime validation is still pending.
- Umbrel packaging is not included yet.
- Realtime WebSocket/SSE delivery is not implemented.
- Automatic filament consumption accounting is not connected to print completion yet.
- Persistent farm scheduling, printer-selection policy and distributed queue leases are not implemented.
- Deep Bambu features such as AMS operations/drying, HMS, K profiles, dual-nozzle control and validated X2D-specific storage remain future typed capabilities.

## Safety notes

FoxForge deliberately refuses to guess whether an ambiguous print start succeeded. Such starts enter `INDETERMINATE` state and are not automatically retried. Receipt-bearing jobs are likewise never blindly redispatched.

Runtime credentials remain in local configuration and are not exposed through public read DTOs. Docker and future Umbrel packaging are expected to use the same application behavior rather than divergent implementations.
